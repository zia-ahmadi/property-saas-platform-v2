4. Unit Availability Management
Three availability states are defined:
Status	Meaning
AVAILABLE	Unit is available for leasing
UNAVAILABLE	Unit is temporarily unavailable
OCCUPIED	Unit is associated with occupancy managed by future lease functionality

The following business rules were implemented:
- Authorized users can change AVAILABLE to UNAVAILABLE and vice versa.
- Repeating the same availability status is accepted as an idempotent operation.
- Manual transitions to or from OCCUPIED are rejected with HTTP 409.
- Availability changes are rejected for archived properties.
- Availability changes are restricted to the correct organization and property.
- Invalid request bodies are rejected with HTTP 400.
The availability endpoint is:
PATCH /api/v1/organizations/{organizationId}/properties/{propertyId}/units/{unitId}/availability


Example request:
{
  "availabilityStatus": "UNAVAILABLE"
}


Successful requests return HTTP 200 with the updated unit response.
5. Security and Tenant Isolation
The module reuses the authentication and authorization infrastructure established in earlier milestones.

Security measures include JWT authentication, PROPERTY_MANAGE permission enforcement for availability updates, organization-context resolution, and tenant-scoped database lookups.

Integration tests verified rejection of unauthorized access, cross-organization requests, and unit identifiers that do not belong to the requested property.
6. Error Handling Improvements
During integration testing, an invalid availability enum value revealed an issue in the shared exception handler.

Previously, an unsupported enum value could produce HTTP 500 rather than HTTP 400.

The GlobalExceptionHandler was updated to handle HttpMessageNotReadableException explicitly.

This change provides consistent client-error responses for malformed JSON and invalid request-body values while preserving the existing ErrorResponse format.
